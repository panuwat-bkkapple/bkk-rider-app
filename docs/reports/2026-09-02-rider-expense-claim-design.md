## 0. ต้องอ่านก่อน — กับดักภาษีที่เปลี่ยนรูปการออกแบบทั้งหมด

> ถ้าออกแบบตามสัญชาตญาณ ("อนุมัติแล้วเติมเงินเข้ากระเป๋าไรเดอร์") **ระบบจะหักภาษี
> จากเงินที่ไม่ใช่เงินได้** และออกใบ 50 ทวิ ที่แจ้งยอดเกินความจริง

**กลไกที่มีอยู่วันนี้ 2 ตัว เมื่อวางต่อกันแล้วให้ผลผิด:**

```js
// bkk-system/functions/rider-wht.js:57-68
function computeRiderWht(grossAmount, employmentType, cfg) {
  const gross = round2(Math.max(0, Number(grossAmount) || 0));   // ← ยอดถอน "ทั้งก้อน"
  ...
  const wht = round2((gross * ratePercent) / 100);
```

```ts
// bkk-rider-app/src/utils/walletLedger.ts:74-79
export function walletBalance(rows) {
  return rows.reduce((acc, t) => t.type === 'CREDIT' ? acc + amt : acc - amt, 0);
}
```

ยอดในกระเป๋าเป็น **ก้อนเดียวไม่แยกที่มา** และ WHT คิดจาก **ยอดถอนทั้งก้อน** →
เงินคืนค่าทางด่วนที่เข้ากระเป๋าจะถูกหัก 3% ตอนถอน

**ทำไมถึงผิด:** เงินคืนค่าใช้จ่ายที่ไรเดอร์สำรองจ่ายแทนบริษัทและมีหลักฐานครบ
**ไม่ใช่เงินได้ของไรเดอร์** — มันคือการคืนต้นทุนที่เขาออกแทนเรา ไม่ใช่ค่าตอบแทน
การหักภาษีจากมันคือการเก็บภาษีจากเงินที่เขาไม่ได้รับ

**ความเสียหายไม่ได้จบที่ 3%** — `onRiderWhtWithheld` ออกใบ 50 ทวิ ต่อการถอนหนึ่งครั้ง
(`bkk-system/functions/rider-wht-issue.js`) ถ้ายอดบนใบเป็นยอดถอนทั้งก้อน
**เอกสารภาษีที่เรายื่น ภ.ง.ด.3 จะแจ้งเงินได้ของไรเดอร์สูงเกินจริง** ซึ่งเป็นปัญหา
ของทั้งเราและเขา และแก้ย้อนหลังยาก

> **หมายเหตุที่ต้องพูดตรงๆ:** ผมออกแบบกลไกให้แยกฐานภาษีได้ถูกต้อง แต่**การตีความ
> ว่ารายการไหนเป็น "เงินได้" หรือ "การคืนเงินทดรอง" เป็นเรื่องที่ต้องยืนยันกับ
> นักบัญชีของบริษัท** — โดยเฉพาะเงื่อนไขว่าต้องมีใบเสร็จในนามบริษัทหรือไม่
> อย่าถือเอกสารนี้เป็นคำแนะนำทางภาษี

### ทางออก: แยก "ฐานภาษี" ออกจาก "ยอดถอน"

```
nonTaxablePool = Σ(credits หมวด EXPENSE_REIMBURSEMENT)
               − Σ(non_taxable_part ของ WITHDRAWAL ที่ผ่านมา)

ตอนถอน X:  nonTaxable = min(X, nonTaxablePool)
           taxable    = X − nonTaxable
           wht        = rate% × taxable        ← ไม่ใช่ × X
```

**คิดจาก ledger ล้วน ไม่ต้องมี state ใหม่** — pool คำนวณจากแถวที่มีอยู่แล้ว

**ทำไมหักส่วนที่ไม่ต้องเสียภาษีออกก่อน:** ลำดับมีผลแค่ *จังหวะ* ไม่มีผลกับ *ยอดรวมทั้งปี* —
เมื่อไรเดอร์ถอนครบ ภาษีสะสม = 3% ของเงินได้ทั้งหมดพอดีไม่ว่าจะเรียงยังไง
เลือกแบบนี้เพราะเข้าใจง่ายที่สุดและเป็นคุณกับไรเดอร์ในระยะสั้น

**ฟิลด์ที่ต้องเพิ่มบน `transactions/{id}` ของการถอน:**

| ฟิลด์ | ความหมาย |
|---|---|
| `amount` | ยอดที่ขอถอน (เหมือนเดิม) |
| `wht_base` | **ส่วนที่เป็นเงินได้** — ตัวที่ใช้คิด WHT และตัวที่ต้องขึ้นบนใบ 50 ทวิ |
| `non_taxable_part` | ส่วนที่เป็นการคืนเงินทดรอง |
| `wht_amount` / `net_paid` | เหมือนเดิม |

**การถอนที่เป็นเงินคืนล้วน → `wht_amount = 0` → ไม่ออกใบ 50 ทวิ** ซึ่งถูกต้อง
(ไม่มีการหักก็ไม่มีอะไรให้รับรอง) และ trigger เดิมทำงานตรงนี้ได้อยู่แล้วเพราะมันดู `wht_amount`

**สิ่งที่ต้องแก้เพิ่มเมื่อทำข้อนี้:** `buildWhtCertificatePdf` ต้องพิมพ์ `wht_base`
ไม่ใช่ `amount` — **ถ้าลืมข้อนี้ กลไกแยกฐานจะถูกต้องแต่เอกสารยังผิด**

## 2. วงจร 3 ขั้น

```
┌─ ไรเดอร์ (bkk-rider-app) ────────────────────────────────────────┐
│ ถ่ายสลิป + เลือกหมวด + กรอกยอด  →  offline queue (แผนรอบก่อน)     │
│                    ↓                                             │
│         callable riderSubmitExpense                              │
└────────────────────┼─────────────────────────────────────────────┘
                     ↓  rider_expenses/{id}  status: submitted
┌─ แอดมิน (bkk-system) ────────────────────────────────────────────┐
│ หน้าใหม่ /rider-expenses — ดูสลิป เทียบกับงาน อนุมัติ/ปฏิเสธ        │
│                    ↓                                             │
│         callable adminReviewExpense                              │
└────────────────────┼─────────────────────────────────────────────┘
                     ↓  เขียน 3 อย่างใน multi-path update เดียว
       ┌─────────────┼─────────────┬──────────────────┐
       ↓             ↓             ↓
  rider_expenses  transactions   expenses
  status: paid    CREDIT         หมวด TRANSPORT
                  EXPENSE_       (P&L ของบริษัท)
                  REIMBURSEMENT
```

### callable ที่ต้องมี 2 ตัว (อยู่ `bkk-system/functions/`)

**`riderSubmitExpense`** — ตรวจก่อนเขียน:
- ผู้เรียกเป็นไรเดอร์ที่มีตัวตนและไม่ถูก Suspended/Rejected *(ใช้เกณฑ์เดียวกับกฎ `/jobs` ที่เพิ่งแก้ใน #928 — อย่าเขียนเงื่อนไขที่สาม)*
- `amount_thb` เป็นจำนวนบวก และ ≤ `hard_max_per_item` · เกิน `manager_max_per_item`
  หรือทำให้ยอดรวมของงานเกิน `ceo_threshold_per_job` → ตั้ง `needs_ceo` (ข้อ 6.2)
- `occurred_at` ไม่เก่ากว่า `hard_backdate_days` · เก่ากว่า `normal_backdate_days`
  → ตั้ง `late` (ข้อ 6.3)
- **`evidence` ต้องมีอย่างน้อย 1 ใบ และ URL ต้องอยู่ใต้ `riders/{ผู้เรียก}/expenses/`** — ไม่งั้นแนบ URL ของคนอื่นได้
- ถ้ามี `job_id` ต้องเป็นงานที่ไรเดอร์คนนี้ถือหรือเคยถือ
- `status` ถูกตั้งเป็น `submitted` **โดย server เสมอ** ไม่รับค่าจาก payload

**`adminReviewExpense`** — gate ด้วย `lookupStaffByAuth` + `canReviewAdjustments` (ข้อ 6.1):
- รายการที่ติด `needs_ceo` ต้องเป็น CEO เท่านั้น MANAGER กดไม่ผ่าน
- อนุมัติ → เขียน 3 โหนดพร้อมกันใน multi-path update เดียว (atomic)
- ปฏิเสธ → บังคับ `reject_reason`
- **idempotent**: รายการที่ `status` ไม่ใช่ `submitted` แล้ว = ปฏิเสธการรีวิวซ้ำ
  (กันกดสองครั้งแล้วเติมเงินสองรอบ — เป็นความพังที่แพงที่สุดของฟีเจอร์นี้)

## 3. เงินเข้ากระเป๋า — หมวดใหม่ + มิเรอร์ 2 ที่

หมวดในกระเป๋าวันนี้เป็น allowlist ปิด 4 ค่า:

```ts
// bkk-rider-app/src/utils/walletLedger.ts:23
export const RIDER_WALLET_CATEGORIES = ['JOB_PAYOUT', 'WITHDRAWAL', 'PENALTY', 'BONUS'] as const;
```

**เพิ่ม `EXPENSE_REIMBURSEMENT` เป็นตัวที่ 5 — ต้องแก้ 2 ไฟล์ (mirror):**

| ไฟล์ | บทบาท |
|---|---|
| `bkk-rider-app/src/utils/walletLedger.ts:23,29-34` | allowlist + ป้ายไทย + `isRiderWalletTx` กรองด้วยเซ็ตนี้ |
| `bkk-system/src/utils/transactionLogger.ts:11` | type union ของ `category` |

**ห้ามใช้ `BONUS` แทนเพื่อเลี่ยงการแก้ mirror** — โบนัสคือเงินได้ (ต้องเสียภาษี)
เงินคืนไม่ใช่ ถ้าปนกันแล้วการแยกฐานภาษีในข้อ 0 ทำไม่ได้เลย และไม่มีใครย้อนแยกได้ทีหลัง

**แถว credit ต้องเขียน `taxable` ลงไปตรงๆ ตั้งแต่ P1 ห้ามอนุมานจากชื่อหมวดทีหลัง**
(ข้อ 6.4) ค่ามาจาก `settings/rider_expense/reimbursement_taxable` — เหตุผลคือคำตอบ
ของนักบัญชียังไม่มา และแถวที่เขียนวันนี้ต้องอ่านได้ถูกไม่ว่าคำตอบจะออกทางไหน
การอนุมานจากหมวดทีหลังแปลว่าเปลี่ยนคำตอบเมื่อไหร่ ความหมายของ**แถวเก่าทุกแถว
เปลี่ยนย้อนหลังตามไปด้วย** ซึ่งเป็นสิ่งที่ ledger ห้ามทำโดยนิยาม

## 4. ลงบัญชี — ห้ามลืม ไม่งั้นกำไรสูงเกินจริง

`/expenses` คือโหนดที่ P&L อ่าน (`bkk-system/src/pages/finance/DailyExpenses.tsx:40`)
หมวดที่มีอยู่: `TRANSPORT` / `SUPPLIES` / `MARKETING` / `MISC` (`:13-18`)

ค่าทางด่วนกับค่าจอดรถ**เป็นต้นทุนของบริษัท** ไม่ใช่แค่หนี้ที่ติดไรเดอร์ —
ถ้าเงินออกจากบริษัทแต่ไม่เคยถูกบันทึกเป็นค่าใช้จ่าย **งบกำไรขาดทุนจะรายงานกำไรสูงเกินจริง**
ทุกเดือนโดยไม่มีใครเห็น

→ ตอนอนุมัติ เขียน `expenses/{id}` หมวด `TRANSPORT` พร้อมฟิลด์เพิ่ม
`rider_id` + `rider_expense_id` เพื่อให้ตามรอยกลับได้และกันการกรอกซ้ำด้วยมือ

**กันนับซ้ำ:** ค่าใช้จ่ายถูกรับรู้ **ครั้งเดียวตอนอนุมัติ** ส่วนเงินในกระเป๋าคือ
*หนี้ที่ต้องจ่าย* ไม่ใช่ค่าใช้จ่ายก้อนที่สอง — **ตอนไรเดอร์ถอนห้ามเขียน `/expenses` อีก**

> **ต้องตรวจก่อนลงมือ:** ค่ารอบไรเดอร์ (`rider_fee`) วันนี้เข้า `/expenses` หรือเปล่า
> ผมยังไม่ได้ไล่ดู — ถ้ามันไม่เข้า แปลว่า P&L ขาดต้นทุนไรเดอร์อยู่แล้วเป็นทุนเดิม
> และควรตัดสินใจให้สองอย่างนี้ใช้กติกาเดียวกัน ไม่ใช่ให้ค่าทางด่วนเข้าแต่ค่ารอบไม่เข้า

**สิ่งที่แผนนั้นออกแบบไว้แล้วและใช้ได้พอดี:**
- `target.key` คำนวณตอน enqueue → **เป็น `expenseId` ตัวเดียวกับที่ callable ใช้** →
  ยิงซ้ำไม่เกิดรายการซ้ำ
- `payload` แก้ได้ขณะอยู่ในคิว → ตรงกับข้อ 3 ("แนบงานทีหลังได้")
- ไม่มี TTL, ล้มถาวรต้องแจ้ง, Blob หาย = `evidence_lost`

**สิ่งที่ต้องเพิ่มจากแผนนั้น:** ขั้น "เขียน record" ของ queue เปลี่ยนจาก
*เขียน RTDB ตรง* เป็น *เรียก callable* — ซึ่งเข้ากับ queue ได้เลยเพราะมันเป็น
job runner ทั่วไปอยู่แล้ว (แผนนั้นข้อ 3) แค่เปลี่ยนตัว executor ของขั้นที่สอง

**หน้าจอที่ไรเดอร์ต้องเห็น** (ต่อจากข้อ 7 ของแผนเดิม):
- รายการเบิกของตัวเอง + สถานะ 4 ค่า พร้อมเหตุผลเมื่อถูกปฏิเสธ
- ยอดที่อนุมัติแล้วต้องแยกให้เห็นในกระเป๋า **ว่าเป็นเงินคืน ไม่ใช่ค่ารอบ** —
  ไม่งั้นตอนถอนแล้วโดนหักไม่เท่ากันเขาจะงงและไม่มีใครอธิบายได้

### 6.3 เส้นตายเบิกย้อนหลัง → **7 วันปกติ · 8-31 วันติดธง `late` · เกิน 31 วันปฏิเสธ**

**ไม่ใช่ TTL ของคิว** (คิวไม่มี TTL ตามที่เคาะไว้รอบก่อน) นี่คือกติกาธุรกิจที่วัดจาก
`occurred_at` ซึ่งไรเดอร์กรอกเอง

- **≤ 7 วัน** = ปกติ ไม่ต้องอธิบายอะไร
- **8-31 วัน** = รับเข้าระบบแต่ติด `late: true` ให้แอดมินเห็นป้ายและตัดสินเอง
  **ไม่ปฏิเสธ** เพราะเหตุผลที่ทำให้ช้าส่วนใหญ่เป็นความผิดของระบบ ไม่ใช่ของไรเดอร์
  (โทรศัพท์พัง ลืม ไม่รู้ว่ามีฟีเจอร์นี้) การปฏิเสธคือการยึดเงินที่เขาจ่ายไปจริง
- **> 31 วัน** = callable ปฏิเสธ พร้อมข้อความให้ติดต่อแอดมินคีย์ให้แทน
  (ทางออกยังมี ไม่ใช่ประตูปิดตาย)

**ทำไม 31 ไม่ใช่ 30 หรือ 60:** `/expenses` ถูกรายงานเป็นราย**เดือนปฏิทินไทย**
(`bangkokYM` → `FinancialReport.tsx`) เพดาน 31 วันรับประกันว่ารายการหนึ่งจะตกงวด
ช้าที่สุดได้แค่**หนึ่งเดือนบัญชี** ไม่มีทางย้อนไปกวนงวดที่ปิดและยื่นภาษีไปแล้ว
(ภ.พ.30 ยื่นวันที่ 15 ของเดือนถัดไป, ภ.ง.ด.3 วันที่ 7)

### 6.4 ภาษี → **ตัดสินแทนไม่ได้ แต่ถอดออกจากทางวิกฤตแล้ว**

การตีความว่าเงินคืนค่าทดรองเป็นเงินได้หรือไม่ **ต้องให้นักบัญชีของบริษัทยืนยัน**

**สิ่งที่ตัดสินได้และตัดสินไปแล้ว คือทำให้คำตอบนั้นมาทีหลังได้โดยไม่ต้อง backfill:**
ทุก credit หมวด `EXPENSE_REIMBURSEMENT` เขียนฟิลด์ `taxable: false` ลงแถวตั้งแต่
P1 **ไม่ใช่ไปอนุมานทีหลังจากชื่อหมวด**

- นักบัญชีตอบว่า "ไม่ใช่เงินได้" → P4 อ่านฟิลด์นี้ตรงๆ ทำงานได้ทันที

  แถวเก่าแก้ด้วย script บรรทัดเดียว **P4 ทั้งเฟสไม่ต้องทำเลย** ซึ่งลดงานลงมาก
- ตอบช้า → P1-P3 เดินต่อได้ปกติ เพราะสวิตช์ `rider_wht.enabled` ยังปิดอยู่

**คำถามที่ต้องถามนักบัญชีมีสองข้อ ไม่ใช่ข้อเดียว:** (1) เงินคืนค่าทดรองนี้เป็น
เงินได้ที่ต้องหัก ณ ที่จ่ายไหม (2) ต้องมีใบเสร็จในนามบริษัทถึงจะลงเป็นค่าใช้จ่าย
ของบริษัทได้ไหม — ข้อ (2) กระทบสิ่งที่ไรเดอร์ต้องถ่ายมา ไม่ใช่แค่เรื่องภาษี

### 6.5 ผล P0 (3 ก.ย. 2569) — ตรวจแล้ว 2 ใน 3 ก้อน

ก่อนเปิดสวิตช์ WHT** ไม่ใช่หลังจากนั้น — ไม่งั้นวันที่เปิดคือวันที่เริ่มหักผิด

## 8. ห้ามทำ

1. **ห้ามเปิด `.write` ของ `rider_expenses` ให้ไคลเอนต์** — บทเรียน P2 (ข้อ 1)
2. **ห้ามใช้หมวด `BONUS` แทนหมวดใหม่** — ปนเงินได้กับเงินคืนแล้วแยกไม่ออกตลอดไป (ข้อ 3)
3. **ห้ามอนุมัติแล้วไม่เขียน `/expenses`** — กำไรสูงเกินจริงเงียบๆ (ข้อ 4)
4. **ห้ามเขียน `/expenses` ซ้ำตอนถอน** — นับต้นทุนสองรอบ (ข้อ 4)
5. **ห้ามให้ `adminReviewExpense` รีวิวรายการที่รีวิวไปแล้ว** — เติมเงินซ้ำ (ข้อ 2)
6. **ห้ามเปิดสวิตช์ WHT ก่อนได้คำตอบนักบัญชี (ข้อ 6.4) และก่อน P4 เสร็จ** — สองเงื่อนไข ไม่ใช่ข้อเดียว
7. **ห้ามให้ยอดบนใบ 50 ทวิ เป็น `amount`** เมื่อทำ P4 แล้ว — ต้องเป็น `wht_base` (ข้อ 0)
8. **ห้ามรับ `status` จาก payload ของ callable** — server ตั้งเองเสมอ (ข้อ 2)

## 9. ยังไม่ได้พิสูจน์ในเอกสารนี้

- ~~ยังไม่ได้ตรวจว่า `rider_fee` เข้า `/expenses` หรือไม่~~ **ตรวจแล้ว 3 ก.ย. — ไม่เข้า ดูข้อ 6.5**
- ยังไม่ได้อ่าน `riderRequestWithdraw` ฝั่ง server ทั้งตัว จึงยังไม่รู้ว่าการเพิ่ม
  `wht_base` / `non_taxable_part` แตะโค้ดตรงไหนบ้างจริงๆ — ต้องอ่านก่อนเริ่ม P4
- ไม่ทราบปริมาณจริง (เบิกกี่ครั้ง/วัน ยอดเฉลี่ยเท่าไร) — เพดานในข้อ 6.2 จึงตั้งจาก
  `min_fee`/`max_fee` ของค่าวิ่งกับราคาทางด่วนจริง **ไม่ใช่จากข้อมูลการเบิกของเราเอง**
  ซึ่งยังไม่มี. ค่าพวกนี้อยู่ใน `settings/rider_expense` แก้ได้โดยไม่ต้อง deploy
  **ต้องกลับมาปรับหลังใช้จริงสักเดือน** ไม่ใช่ตั้งแล้วลืม
- **การตีความภาษีทั้งหมดในข้อ 0 ต้องให้นักบัญชียืนยัน** ผมออกแบบกลไกให้รองรับ
  ทั้งสองคำตอบได้ แต่ไม่ได้เป็นคนตัดสินว่าคำตอบคืออะไร
