# แผน: Offline queue ของการแนบหลักฐาน (แอปไรเดอร์) — 1 ก.ย. 2569

> **ต่อจาก** `docs/reports/2026-09-01-rider-expense-evidence-survey.md` ซึ่งสรุปว่า
> ตัวอัปโหลดใช้ซ้ำได้ แต่ **ไม่มี retry / queue / offline persistence เลย** —
> เอกสารนี้คือแผนปิดช่องนั้น
>
> **เป็นแผน ยังไม่ได้เขียนโค้ด** · ขอบเขตยังเป็นเรื่องรูปหลักฐานเท่านั้น
> (approval flow / สถานะการเบิก / การจ่ายเงิน อยู่นอกแผนนี้ตามที่ตกลง)
>
> ยังไม่ได้สำรวจฝั่ง bkk-system — จุดที่แผนนี้ไปแตะฝั่งนั้นถูกทำเครื่องหมาย **[ฝั่ง admin]**
> ไว้เป็นข้อสังเกต ไม่ใช่ข้อสรุป

## 1. โจทย์จริง ไม่ใช่โจทย์ทั่วไป

ค่าทางด่วนกับค่าจอดรถ **เกิดขึ้นในที่ที่ไม่มีสัญญาณพอดี** — ด่านใต้ทางยกระดับ, ลานจอดใต้ดินห้าง,
ชั้น B2 ของคอนโด. เงื่อนไข "ไม่มีรูป = ส่งไม่ได้" บวกกับสภาพวันนี้ (`survey` ข้อ 4) แปลว่า
**ไรเดอร์จะกดส่งไม่ได้เลยตรงจุดที่เกิดค่าใช้จ่าย** และถ้าเขาปิดแอปไปก่อน งานที่กรอกไว้หายทั้งหมด

นี่ไม่ใช่ปัญหา UX เฉยๆ — มันคือ **เงินของไรเดอร์ที่หายเงียบ** ซึ่งเป็นความพังประเภทที่
ไม่มี error ไม่มีใครแจ้ง และรู้ตัวอีกทีตอนสิ้นเดือนว่าเบิกไม่ครบ

## 2. ข้อเท็จจริงของแพลตฟอร์มที่บังคับรูปทรงของคำตอบ (ตรวจแล้ว)

| ข้อเท็จจริง | ผลต่อการออกแบบ | สถานะการตรวจ |
|---|---|---|
| **iOS/Safari ไม่มี Background Sync API** และไม่มีกำหนดจะทำ | **flush ต้องเกิดตอนแอปเปิดอยู่เท่านั้น** — ห้ามออกแบบโดยพึ่ง background sync เป็นทางหลัก | ยืนยันแล้ว (แหล่งอ้างอิงท้ายไฟล์) |
| **ITP ลบ script-writeable storage ทั้งหมด (รวม IndexedDB) หลังไม่มีการใช้งาน 7 วัน** แต่ **โดเมนของ web app ที่ Add to Home Screen ได้รับการยกเว้น** | queue ปลอดภัยเฉพาะเมื่อไรเดอร์ใช้ผ่านไอคอนหน้าจอโฮม — **คนที่เปิดใน tab Safari ปกติมีสิทธิ์โดนลบ queue ทิ้ง** | ยืนยันแล้ว (แหล่งอ้างอิงท้ายไฟล์) |
| manifest ตั้ง `"display": "standalone"` แล้ว (`public/manifest.json`) แต่ **ไม่มีโค้ดตรวจว่ากำลังรันแบบ standalone อยู่จริงหรือไม่** (`grep "display-mode\|standalone" src/` = 0) | ต้องเพิ่มการตรวจ + เตือน ถ้าจะพึ่ง IndexedDB เก็บเงิน | ตรวจแล้วในโค้ด |
| **RTDB web SDK ไม่มี disk persistence** (มีแค่คิวในหน่วยความจำ หายเมื่อรีเฟรช) | เขียน `set()`/`update()` ตอนออฟไลน์แล้วปิดแอป = **ข้อมูลหาย** → คิวต้องเป็นของเราเอง ไม่ใช่ของ SDK | ทราบจากพฤติกรรม SDK — **P0 ต้องเทสจริงหนึ่งรอบก่อนพึ่งพา** |
| ใช้ `uploadBytes` ไม่ใช่ `uploadBytesResumable` (`src/utils/uploadImage.ts:2,61`) | ไม่มี resume — งานที่ขาดกลางคันต้อง **อัปใหม่ทั้งไฟล์** ซึ่งยอมรับได้เพราะไฟล์ถูกบีบเหลือ ≤0.8 MB (`:6-10`) | ตรวจแล้วในโค้ด |
| Service worker แตะเฉพาะ GET (`public/firebase-messaging-sw.js:48-50`) และไม่มี `sync` listener | **ห้ามแก้ SW ให้ดักการอัปโหลด** — SW ตัวนี้เคยพังจนไม่ activate มาแล้ว (comment `:8-11`) และการดัก POST ของ Storage คือการรับหนี้ก้อนใหม่โดยไม่จำเป็น | ตรวจแล้วในโค้ด |

**ข้อสรุปจากตารางนี้:** queue ต้องเป็น **โค้ด application ธรรมดา + IndexedDB + flush ตอน foreground**
ไม่ใช่ service worker และไม่ใช่ Background Sync (จะใส่ Background Sync เป็น *ของแถม* สำหรับ Chrome/Android
ทีหลังก็ได้ แต่ต้องไม่มีอะไรในระบบพึ่งมัน)

## 3. การตัดสินใจสถาปัตยกรรมข้อเดียวที่สำคัญที่สุด

> **queue ต้องไม่รู้จักคำว่า "ค่าใช้จ่าย"**

มันคือ **job runner ทั่วไป** ที่รับงานรูปแบบ *"อัปไฟล์ชุดนี้ให้เสร็จ แล้วเขียน record นี้ลง path นี้"*
ฟีเจอร์เบิกค่าใช้จ่ายเป็นแค่ **คนป้อนงานคนแรก**

เหตุผล 3 ข้อ:
1. **มันทำให้แผนนี้ไม่ล้ำเข้าไปในเรื่องที่เจ้าของงานกันไว้** (approval / สถานะ / การจ่ายเงิน) —
   queue ไม่ต้องรู้ว่าปลายทางคือโหนดอะไร มีสถานะอะไรบ้าง ใครอนุมัติ
2. **ปัญหาเดียวกันมีอยู่แล้วอีก 11 จุด** (`survey` ข้อ 1) — KYC, รูปสภาพเครื่อง, amendment
   ทุกตัวพังแบบเดียวกันตอนเน็ตหลุด การเขียน queue เฉพาะกิจให้ค่าใช้จ่ายคือการรับประกันว่า
   จะต้องเขียนตัวที่สองอีกในอีกสามเดือน (และตัวที่สองจะไม่ตรงกับตัวแรก — เหมือนทุกเคส
   mirror ใน CLAUDE.md)
3. **มันทดสอบได้** — logic ของ queue กลายเป็นฟังก์ชัน pure ที่ vitest จับได้ทั้งหมด
   (ดูข้อ 9) ต่างจากการฝัง retry ไว้ในปุ่ม submit ซึ่งเทสได้แค่ผ่าน DOM

**แต่ยังไม่เปิดใช้กับ 11 จุดเดิมในรอบนี้** — เขียนให้ generic แต่ต่อสายเฉพาะค่าใช้จ่าย
(ดูเฟส P4 และ "สิ่งที่ห้ามทำ" ข้อ 7)

## 4. โครงของ queue item

```ts
// src/utils/uploadQueue/types.ts  (เสนอ)
interface QueuedUpload {
  id: string;              // UUID ฝั่ง client — เป็น idempotency key ของทั้งงาน
  uid: string;             // เจ้าของงาน = auth.uid ตอน enqueue
  created_at: number;      // เวลาเครื่องไรเดอร์ ตอนกดส่ง
  kind: 'expense_evidence'; // ป้ายบอกที่มา (ไว้ debug/metric เท่านั้น ไม่มี logic ผูก)

  files: QueuedFile[];     // ไฟล์ที่บีบอัดแล้ว
  target: {
    path: string;          // RTDB path ที่จะเขียน — ผู้เรียกคำนวณมาให้แล้ว
    payload: Record<string, unknown>; // record ที่จะเขียน (ยังไม่มี url ของรูป)
    urlField: string;      // ชื่อฟิลด์ที่จะยัด url[] ลงไปตอนอัปครบ
  };

  state: 'pending' | 'uploading' | 'failed_permanent';
  attempts: number;
  next_attempt_at: number; // backoff
  last_error?: string;     // ข้อความที่ไรเดอร์อ่านรู้เรื่อง
  leased_until?: number;   // กัน flush สองตัวหยิบงานเดียวกัน
}

interface QueuedFile {
  blob: Blob;              // เก็บ Blob ตรงๆ ได้ IndexedDB รองรับ structured clone
  storage_path: string;    // คำนวณตอน enqueue — คงที่ตลอดชีพของงาน
  url?: string;            // มีค่าแล้ว = ไฟล์นี้ขึ้นแล้ว ห้ามอัปซ้ำ
}
```

**จุดที่ตั้งใจ ไม่ใช่รายละเอียด:**

- **`storage_path` ถูกคำนวณตอน enqueue ไม่ใช่ตอน upload** → retry เขียนทับ object เดิมเสมอ
  = **idempotent โดยโครงสร้าง** ไม่ต้องมี logic dedupe ที่ไหนเลย
  (นี่คือเหตุผลที่ path ของค่าใช้จ่าย **ห้าม** ใช้กติกา write-once ของ KYC —
  `bkk-frontend-next/storage.rules:144-147` `allow create ... allow update: if false`
  จะทำให้ retry ครั้งที่สองถูกปฏิเสธถาวร ดู `survey` ข้อ 6)
- **`files[].url` เป็น state ต่อไฟล์** → อัป 3 ใบ ล้มใบที่ 3 แล้ว retry จะอัปเฉพาะใบที่ 3
  ต่างจากของเดิมที่ `Promise.all` ทิ้งทั้งชุดและทิ้ง orphan ไว้ใน Storage
  (`src/components/amendments/RequestAmendmentModal.tsx:230-243`)
- **`target.path` ถูกคำนวณตอน enqueue ด้วย `push(ref(db, ...)).key`** ซึ่ง SDK สร้าง key
  ฝั่ง client (pattern เดียวกับที่ `src/hooks/useJobActions.ts:427-428` ใช้อยู่แล้ว) →
  งานที่ retry เขียนลง key เดิม = **ไม่มีแถวซ้ำแม้ flush จะรันซ้อนกัน**
- **`uid` ติดมากับงาน** → ถ้าไรเดอร์คนที่สอง login เครื่องเดียวกัน flush จะข้ามงานของคนแรก
  **ไม่ใช่ลบทิ้ง** (ดู "สิ่งที่ห้ามทำ" ข้อ 5)

## 5. Invariant ที่ห้ามละเมิด

1. **รูปต้องขึ้นครบก่อน record จะถูกเขียน** — ลำดับคือ `อัปทุกไฟล์ → ได้ url ครบ → เขียน RTDB`
   ถ้ากลับลำดับจะได้แถวเบิกเงินที่ไม่มีหลักฐาน ซึ่งละเมิดกฎ "ไม่มีรูป = ส่งไม่ได้"
   ที่เป็นเหตุผลทั้งหมดของฟีเจอร์นี้
2. **งานหนึ่งชิ้นสร้างแถวได้ไม่เกินหนึ่งแถว** — บังคับด้วย client-generated key (ข้อ 4)
   ไม่ใช่ด้วยการล็อกหรือการเช็คก่อนเขียน
3. **flush เป็น single-flight** — `online` event กับ `visibilitychange` ยิงพร้อมกันได้จริง
   ต้องมี mutex ในหน่วยความจำ + `leased_until` ใน record กันเคสหลาย tab
4. **error ถาวรต้องหยุด ไม่ใช่ retry ตลอดกาล** — แยกสองกลุ่ม:
   - *retryable*: network error, `storage/retry-limit-exceeded`, token หมดอายุ → backoff แล้วลองใหม่
   - *ถาวร*: `storage/unauthorized` (rules ปฏิเสธ), ไฟล์ไม่ผ่าน `validateImageFile`
     (`src/utils/uploadImage.ts:15-23`), `permission_denied` ของ RTDB
     → `failed_permanent` + โผล่ใน UI ให้ไรเดอร์เห็น **ห้ามลบทิ้งเอง**
5. **queue ต้องมองเห็นได้เสมอ** — queue ที่ทำงานเงียบคือ queue ที่ไรเดอร์ไม่รู้ว่าเงินยังไม่ถึง
   ซึ่งแย่กว่า toast แดงของวันนี้ (ดูข้อ 7)
6. **ห้าม throw ออกจาก flush ไปถึง UI** — flush ทำงานเบื้องหลัง ความล้มเหลวสื่อสารผ่าน state ของ item

## 6. เมื่อไหร่ที่ flush ทำงาน

เรียงตามความสำคัญ (ทั้งหมดเป็น foreground เพราะข้อ 2):

1. **ทันทีหลัง enqueue** (ถ้าออนไลน์อยู่) — เคสปกติ 99% ต้องรู้สึกเหมือนไม่มี queue อยู่เลย
2. **`window` event `online`** — ตัวเดิมที่ `src/components/common/OfflineBanner.tsx:24-25` ใช้อยู่แล้ว
3. **`visibilitychange` → `visible`** — เคสจริงบน iOS: ไรเดอร์ขับออกจากลานจอด หน้าจอดับ
   `online` อาจไม่ยิง แต่การกลับมาเปิดแอปยิงแน่นอน
4. **ตอนแอปบูต หลัง auth settle** — ไม่ใช่ตอน mount (token ยังไม่พร้อม upload จะล้มทันที)
5. **timer ขณะออนไลน์** ทุก ~30 วิ เฉพาะเมื่อมีงานค้างและถึง `next_attempt_at` แล้ว —
   ตาข่ายกันตกสำหรับเคส "เน็ตมาแบบ event ไม่ยิง" (เจอบ่อยบนมือถือที่สลับ 4G/Wi-Fi)

`navigator.onLine` **ใช้เป็นตัวเร่ง ไม่ใช่ตัวตัดสิน** — มันรายงาน `true` ได้ทั้งที่ออกเน็ตไม่ได้จริง
(captive portal, Wi-Fi ห้างที่ยังไม่ล็อกอิน) การตัดสินจริงคือผลของ `uploadBytes` เอง

**Backoff:** 5s → 15s → 1m → 5m → 15m แล้วคงที่ 15m (มีเพดาน ไม่ใช่ exponential ไม่จำกัด
เพราะไรเดอร์เปิดแอปอยู่ตรงหน้า การรอเกิน 15 นาทีไม่มีประโยชน์)

## 7. UI ที่บังคับต้องมี (ไม่ใช่ nice-to-have)

- **ตัวนับงานค้างที่เห็นจากหน้าหลัก** — "รอส่ง N รายการ" ไม่ใช่ซ่อนในหน้าลึก
- **สถานะต่อรายการ**: กำลังส่ง / รอสัญญาณ / ส่งไม่สำเร็จ + เหตุผลภาษาคน
- **ปุ่มลองใหม่ด้วยมือ** สำหรับรายการที่ `failed_permanent`
- **ปุ่มลบ** ที่ต้องกดยืนยัน — เจ้าของเงินต้องเป็นคนตัดสินใจทิ้ง ไม่ใช่ระบบ
- **คำเตือนเมื่อไม่ได้รันแบบ standalone** (ถ้ามีงานค้างและ `matchMedia('(display-mode: standalone)')`
  เป็นเท็จบน iOS) — เพราะนั่นคือสภาพที่ ITP ลบ queue ทิ้งได้ใน 7 วัน (ข้อ 2)
- ใช้ `toast` เดิม (`src/components/common/Toast.tsx:15-19`) สำหรับ feedback ชั่วคราว
  แต่ **สถานะถาวรต้องไม่อยู่ใน toast** (toast หายเองใน 3.5 วิ — `:35`)

เทสที่เขียนตามเคสจริงจับบั๊กได้ ส่วนเทสที่เขียนตาม UI ที่มีอยู่แล้วจะยืนยัน UI นั้น

## 9. เทส (ตามกฎของ repo)

เทสหลักเป็น **pure unit test** ที่ `src/utils/uploadQueue/*.test.ts` ตามแบบ
`src/utils/walletLedger.test.ts` (ซึ่งเขียนจากข้อมูล production จริง ไม่ใช่จาก spec)

เคสที่ต้องมี — **เขียนจากสถานการณ์จริงของไรเดอร์ ไม่ใช่จากตาราง state**:
1. ลานจอดใต้ดิน: enqueue ตอนออฟไลน์ → ขึ้นมาชั้นบน → flush → แถวเดียว รูปครบ
2. อัป 3 ใบ ล้มใบที่ 3 → retry อัปเฉพาะใบที่ 3 (ใบ 1-2 ต้อง**ไม่**ถูกอัปซ้ำ)
3. flush สองตัวยิงพร้อมกัน (`online` + `visibilitychange`) → งานถูกหยิบครั้งเดียว
4. `storage/unauthorized` → `failed_permanent` ทันที ไม่ retry
5. network error → backoff ตามลำดับที่กำหนด ไม่เกินเพดาน
6. ไรเดอร์คนที่สอง login → งานของคนแรกไม่ถูก flush และไม่ถูกลบ
7. record เขียนสำเร็จแล้วแอปถูกปิดก่อนลบงานออกจาก queue → รอบหน้าเขียนซ้ำ path เดิม = ไม่เกิดแถวที่สอง

**Injection test บังคับ** ตามกฎ CLAUDE.md (`commit checkpoint ก่อนเสมอ`) — ทำลายทีละกฎ
แล้วเทสต้องแดง:
- ตัด `leased_until` ทิ้ง → เคส 3 ต้องแดง
- ให้ `classifyError` คืน retryable ทุกกรณี → เคส 4 ต้องแดง
- ให้ `storage_path` สุ่มใหม่ทุกครั้งที่ upload → เคส 2 หรือ 7 ต้องแดง
- ให้ flush ข้ามการเช็ค `uid` → เคส 6 ต้องแดง

**ถอดทีละคู่ด้วย** — โดยเฉพาะ `leased_until` คู่กับ mutex ในหน่วยความจำ ซึ่งเป็นคู่ที่
กลบกันเองได้พอดีตามกับดักข้อ 1 ในหัวข้อ Injection test ของ CLAUDE.md

## 10. สิ่งที่ห้ามทำ

1. **ห้ามพึ่ง Background Sync เป็นทางหลัก** — iOS ไม่มี (ข้อ 2) ใส่เป็นของแถมของ Android ได้ทีหลัง
2. **ห้ามเก็บรูปเป็น base64 ใน localStorage** — โควตา ~5 MB, เขียนแบบ synchronous บล็อก main thread,
   และ base64 ทำให้ไฟล์ใหญ่ขึ้น ~33%
3. **ห้ามให้ queue เขียน record ก่อนรูปขึ้นครบ** (invariant ข้อ 1)
4. **ห้าม retry ไม่จำกัดกับ error ถาวร** — โดยเฉพาะ `storage/unauthorized` ซึ่งแปลว่า
   rules ปฏิเสธ และจะปฏิเสธเหมือนเดิมทุกครั้งจนกว่าจะมีคน deploy rules ใหม่
5. **ห้ามล้าง queue ตอน logout** — งานค้างคือเงินที่ยังไม่ได้เบิก การล้างคือการทำเงินหายเงียบ
   (เทียบกับ `handleAuthTransition` ฝั่งเว็บลูกค้าที่ล้างตะกร้าตอน logout — **คนละเรื่องกัน**
   ตะกร้าสร้างใหม่ได้ สลิปที่ถ่ายไว้ใบเดียวสร้างใหม่ไม่ได้)
6. **ห้ามแก้ service worker ให้ดักการอัปโหลด** (ข้อ 2 แถวสุดท้าย)
7. **ห้ามต่อ queue เข้ากับ 11 จุดเดิมในรอบนี้** — โดยเฉพาะ KYC ซึ่ง rule เป็น
   `allow create` + `allow update: if false` (`storage.rules:144-147`) แปลว่า retry
   ที่เขียนทับ path เดิมจะถูกปฏิเสธ **queue รุ่นแรกยังไม่รองรับ semantics นี้**
8. **ห้ามใช้ queue เป็นข้ออ้างให้ UI บอกว่า "ส่งสำเร็จ"** ถ้ายังไม่ถึง server —
   ข้อความต้องเป็น "บันทึกแล้ว รอส่งขึ้นระบบ" ตรงไปตรงมา

## 11. คำถามที่ต้องให้เจ้าของงานตัดสิน (ตอบก่อนเริ่ม P1)

**1. กดส่งตอนออฟไลน์ = "ส่งแล้ว" หรือ "ยังส่งไม่ได้"?**
- *(ก) แบบ optimistic (เสนอ)* — กดได้ทันที ขึ้นสถานะ "รอส่งขึ้นระบบ" แล้วไปเองเมื่อมีเน็ต
  ได้ประโยชน์เต็มของ queue แต่ **[ฝั่ง admin]** แถวเบิกจะโผล่ช้ากว่าเวลาที่เกิดจริงได้เป็นชั่วโมง
- *(ข) แบบบล็อก* — ต้องมีเน็ตถึงกดส่งได้ queue ทำหน้าที่แค่กันฟอร์ม+รูปหาย
  ง่ายกว่ามาก ไม่มีผลต่อฝั่ง admin เลย แต่ไรเดอร์ยังต้องกลับมากดเอง

**2. Storage path** — กระทบว่าต้อง deploy rules ข้าม repo หรือไม่
- *(ก) `riders/{uid}/expenses/{expenseId}/{uuid}.jpg` (เสนอ)* — **ไม่ต้องแก้ rules เลย**
  rule `storage.rules:310-315` ใช้ `{filename=**}` และ `auth.uid == riderId` ครอบอยู่แล้ว
  ได้ self-write scope ฟรี (ไรเดอร์เขียนโฟลเดอร์คนอื่นไม่ได้ ซึ่ง `jobs/**` ทุก path ทำไม่ได้)
- *(ข) `jobs/{jobId}/expenses/...`* — ตรงความหมายกว่าถ้าค่าใช้จ่ายผูกกับงานใบหนึ่ง
  แต่ **ต้องเพิ่ม rule block และ deploy จาก bkk-frontend-next** ซึ่งเป็น workflow แยก
  (CLAUDE.md: deploy rules อยู่คนละ workflow กับ CI และเคยแดงเงียบมาแล้ว 3 รอบ)

**3. ค่าใช้จ่ายผูกกับ "งาน" หรือ "รอบ/กะ"?** — ถ้าผูกกับรอบ ตัวเลือก 2(ข) ตกไปเอง
และ **[ฝั่ง admin]** ต้องมีที่ยืนใหม่ เพราะวันนี้ไม่มีหน้าไหนดูรูปของไรเดอร์แบบไม่ผูกกับงาน
ยกเว้น `/riders` (`survey` ข้อ 5)

**4. งานที่ค้างเกิน N วันให้ทำอย่างไร?** — เสนอ: ไม่ลบอัตโนมัติ แต่ขึ้นเตือนที่ 3 วัน
และให้ไรเดอร์ตัดสินใจเอง (ห้ามระบบทิ้งเงินของคน)

## 12. สิ่งที่ยังไม่ได้พิสูจน์ในเอกสารนี้

- ยังไม่ได้เทสบนเครื่องจริงเลยสักข้อ — ทั้งหมดอยู่ใน P0
- ไม่รู้ปริมาณจริง: ไรเดอร์เบิกกี่ครั้งต่อวัน กี่รูปต่อครั้ง — ตัวเลขนี้เปลี่ยนเพดานโควตา
  และความคุ้มของ P4 ได้
- ยังไม่ได้สำรวจ bkk-system จึง **ไม่ทราบว่าฝั่ง admin ต้องแก้อะไรบ้าง** เพื่อรับแถวที่มาช้า
  (จุดที่ทำเครื่องหมาย **[ฝั่ง admin]** ไว้คือที่ที่น่าจะต้องดู)
- `node_modules` ไม่ได้ติดตั้งใน container นี้ จึงยังไม่ได้ตรวจว่า Firebase SDK เวอร์ชันที่ pin ไว้
  (`firebase ^10.13.0`) มี retry ภายในแค่ไหน — ซึ่งอาจทำให้ backoff ชั้นของเราซ้อนกับของ SDK
